1 · TL;DR

Verdict

Direction: yes, but compress it. The instinct — C# as the authoring surface for workflow structure and contracts, with workflow YAML as the emitted artifact — is supported by every prior-art family worth copying (CDK, Flyte, Dagger) and by all three reviewers. But every reviewer also said: not as the full vision, not now, and not as a vehicle to replace conductor.

Action: ship compiler-lite first — a typed C# contract registry (verb signatures, agent outputs, workflow I/O) consumed by schema-driven YAML lint and route validation. Stop and measure before promoting it to a full authoring DSL.

  • Build-time, not JIT. Every report and every reviewer rejected runtime YAML generation as the default. Build-time emission keeps the artifact reviewable, the harness in the loop, and AOT realistic.
  • Conductor stays the runtime. Option A in Inv 3. The dashboard, human-gate UI, /api/stop, event log, and for_each engine are too valuable to rebuild for a typing win.
  • The agent contract boundary is the highest-value target. The architect → write-plan → seed-children trace in Inv 4 is the worst stringly drift in the repo; one named PlannerOutput/PlannedChild contract collapses prompt schema, route vocab, CLI bindings, and sidecar parsers into one declaration.
  • Ride the sibling tracks. AB#3255 typed-contract-surface is compiler-lite Phase 0/1. AB#3256 matrix-collapse must land before any authoring DSL is frozen. AB#3258 shrinks the opaque-script surface. AB#3257 is independent — do not absorb it.
  • Compiler-lite may be the finish line. R3 explicitly: governance must bless stopping there if 60-80% of the pain is gone. Path-dependence is the enemy.
  • What C# can prove. Field existence, producer/consumer compatibility, child-input completeness, route reads, enum exhaustiveness (with analyzer), null/omit discipline, kind-level resource subsetting.
  • What C# cannot prove. Prompt truthfulness, agent honesty, tool obedience, remote ADO legality, runtime set membership, concrete resource identity closure, human gate decisions.
  • The 6-month win is not "everything in C#." It is: AB#3255 landed, AB#3256 stabilized, compiler-lite in CI, 1–3 small workflows pilot-generated side-by-side, and enough data to know whether the full DSL is worth a second 6 months.

2 · The question Daniel asked

"Should we find a way to declare everything in C# and use that to generate the workflow just in time? If we do that, we can eventually basically make a workflow compiler for handling specific shapes of work." — Daniel, framing the investigation

Three things are bundled in that question, and the synthesis pulls them apart:

Declare in C#

Move workflow structure and contracts into a typed host language. Verdict: supported, but narrowly — the structural seams (verbs, agents, routes, child workflows, counters, resources), not the soul (prompt prose, gate rubrics, eval heuristics).

Generate just-in-time

Emit YAML at the moment of dispatch. Verdict: unanimously deprecated. Build-time emission wins on inspectability, harness compatibility, AOT posture, and on-call debuggability. JIT is opt-in, narrow, cached, and rare.

Eventually a compiler for shapes of work

An L3-style work-shape library: "implement MG", "open PR", "actionable evidence loop". Verdict: plausible long-term, but only after compiler-lite proves its keep and the L2 layer has at least one season of use. Do not skip ahead.

3 · Where everyone agreed

All 5 investigators converged on:

  • The closest industry analogs are CDK (structural), Flyte (operational), and Dagger (ergonomic) — not Temporal/DBOS (durable-execution-as-code). Inv 1
  • Build-time emission + Roslyn analyzers, seeded by the existing PolyphonyJsonContext / VerbOutputSchemaCatalog pattern. Source-generator first; no runtime reflection registry. Inv 2
  • Option A — keep conductor as runtime, emit YAML at build. Options B (JIT), C (replace conductor), and D (shared plan protocol) are not the first move. Inv 3
  • The highest-leverage target is the agent contract boundary, where one named DTO must replace today's prompt×YAML×CLI×sidecar quadruplication. Inv 4
  • Ship compiler-lite, not a full compiler. Use AB#3255 as substrate. Land AB#3256 before freezing any authoring DSL. Treat AB#3257 as independent. Migration discipline, not code generation, is the long pole. Inv 5

All 3 reviewers converged on:

  • "Qualify, not endorse." Every reviewer signed off on compiler-lite / build-time emission, and every reviewer drew a hard line at scope creep.
  • The compiler cannot prove agent truthfulness. Schemas, route vocabularies, and capability declarations are descriptions — not enforcement. R1 R2
  • Conductor must not be replaced. Becoming a multi-agent orchestration platform is a different program. R2 R3
  • Generated artifacts must stay first-class. Hidden execution plans wreck the on-call story. R1 R3
  • The harness remains authoritative. Real conductor against real YAML — compiler tests are added, not substituted. R1
  • Prompt prose stays human-authored. The compiler owns only the load-bearing contract fragments inside prompts. R2 R3
Convergence The collective answer is unusually consistent. Eight independent reads, one shape: typed authority + emitted artifact + conductor runtime + agent contract focus + compiler-lite first. Where consensus is this tight, the synthesis question becomes how aggressively to shrink the proposal, not whether to do it.

4 · Where they disagreed

Tension Bullish side Skeptical side Resolution
How big the v1 surface should be Inv 2 sketches a fluent builder covering scripts, agents, gates, counters, sub-workflows, resources, and exports — all in one go. R3 flags this as "four systems under one name" (contracts, builder, generators, artifacts) and warns against accidental compiler engineering. Compiler-lite first. Builder is the long-term goal, not v1. v1 is descriptors + lints over existing YAML.
What the first pilot proves Inv 5 recommends a leaf workflow (e.g. root-fallback-gate) — smallest surface for emitter ergonomics. R2 counters: a non-agent pilot under-tests the boundary where agentic systems actually break. Demands a parallel "small but real agent contract" pilot. Two pilots in parallel: one leaf for emitter ergonomics, one agent-bearing for contract drift — both side-by-side with handwritten canon.
Where to land long-term Inv 3 sees Option D (shared typed plan protocol) as the only credible upgrade past A. R3 insists "stop at A or compiler-lite" is also a credible end state. Path-dependence is not destiny. Stop is an option. Bless it explicitly in the brief so compiler-lite is a real off-ramp.
Enum overlay vs. discriminated unions Inv 2 casually mentions "generated unions" as a natural refinement. R1: C# 12/.NET 9 has no native sum types. Going from enum overlay to sealed-record union is a real complexity step, requires a Roslyn exhaustiveness analyzer, and is not a free refinement. v1 = enum overlays + analyzer. Sealed unions only when payload-bearing variants justify them. Honest about the language ceiling.
How much resource modeling to promise Inv 2: D13 attributes + journal effects let the compiler enforce "workflow can only own these resources." R1: kind subset, yes. Pattern compatibility, sometimes. Concrete ownership closure, no — resource ids derive from runtime values, scripts are opaque, agents mutate directly. Promise kind-subset only in v1. Pattern checks as analyzer warnings. Ownership closure stays a runtime/drift concern.
Schema strictness at the agent boundary R1 instinct: strict schemas, fail hard, prove more. R2: required-field pressure causes models to fabricate. Need strict-core / soft-perimeter / explicit refusal variants. Strict required core, optional advisory periphery, mandatory refusal/abstain variant on every agent contract.
Whether non-C# authorship matters Inv 2: non-C# authorship is "probably a non-goal." R3: ❌ overstated. Operators, incident responders, onboarding contributors, and future AI assistants still need a legible compiled surface. Emitted YAML stays first-class, checked-in during migration, with stable node names and source maps.

6 · What compiler-lite means concretely

Compiler-lite is not "write workflows in C#." It is a typed C# registry of every cross-boundary contract the existing handwritten workflows depend on, plus a Roslyn-driven lint that holds the YAML to it.

Inputs (you already have these or are building them)

  • [Command] + [VerbResult] annotated verb methods (already authoritative in src/Polyphony/Commands/)
  • PolyphonyJsonContext source-generated JSON contracts
  • VerbOutputSchemaCatalog (already shipped)
  • AB#3255 envelope lint + typed contract surface (in flight)

Outputs the compiler-lite slice adds

  • Typed agent contracts — one named DTO per agent (e.g. PlannerOutput, PlanReviewerOutput, ScopeReviewOutput) carrying route-critical core + optional periphery + mandatory refusal variant.
  • Typed workflow I/O records — one record each for FeaturePrInput/FeaturePrOutput and the rest, generated into a contract catalog.
  • Generic envelope lint — YAML {{ node.output.x }} references resolve against the declared producer contract; route conditions resolve against declared enums; child-workflow call sites must satisfy declared WorkflowDescriptor<TIn,TOut>.
  • Generated enum overlays for the existing string discriminants: BranchNextImplAction, ReviewVerdict, ResearchRequestKind, PrPlatform.
  • Roslyn exhaustiveness analyzer — route tables over enums must cover every variant or include an explicit catch-all marked as such.

Pseudo-C# — the surface a compiler-lite consumer sees

// 1. Generated from existing [Command] + [VerbResult] methods.
//    No hand-maintained second source of truth.
public static partial class PolyphonyVerbs
{
    public static class Branch
    {
        public static VerbDescriptor<BranchNextImplArgs, BranchNextImplResult> NextImpl { get; }
            = GeneratedVerbs.Branch_NextImpl;
    }
}

// 2. Generated enum overlay over the existing string discriminant.
//    The string field stays for wire compatibility; the enum is the typed view.
public enum BranchNextImplAction
{
    ImplementItem,
    AllItemsDone,
    Error
}

public sealed partial record BranchNextImplResult
{
    public BranchNextImplAction ActionKind => BranchNextImplActionCodec.Parse(Action);
}

// 3. One agent contract DTO — route-critical core, optional periphery,
//    mandatory refusal/abstain variant. Used by prompt fragment generation,
//    YAML output schema lint, route validator, CLI binding lint, and sidecar parser.
public sealed record PlannerOutput
{
    public required string Plan { get; init; }
    public required IReadOnlyList<PlannedChild> Children { get; init; }
    public required ResearchRequestKind ResearchRequestKind { get; init; }
    public IReadOnlyList<OpenQuestion> OpenQuestions { get; init; } = [];
    public AgentRefusal? Refusal { get; init; }   // explicit insufficient-context
}

public sealed record PlannedChild
{
    public required string ChildId { get; init; }      // stable across replans
    public required string Title { get; init; }
    public required WorkItemType Type { get; init; }
    public required IReadOnlyList<string> AcceptanceCriteria { get; init; }
    public string? Pg { get; init; }
    public IReadOnlyList<string> DependsOn { get; init; } = [];
}
What this buys Once PlannerOutput is the one declaration, the YAML output: schema, the route table on research_request_kind, the --children-json CLI binding, PlanCommands.WritePlan's parser, and plan-{id}.children.json's sidecar all collapse into projections of one C# record. The compiler-lite slice is delivering this for every agent.

What the lint catches at build time

// In the still-handwritten implement-merge-group.yaml:
- to: impl_branch_ensure
  when: "{{ root_router.output.actoin == 'implement_item' }}"
                                       ^
// WF0012: route reads field 'actoin' but producer BranchNextImplResult
//         declares no such field. Did you mean 'action'?

- name: write_plan
  args:
    - "--children-json"
    - "{{ architect.output.kids | tojson }}"
                              ^
// WF0014: 'architect.output.kids' is undefined; PlannerOutput declares
//         { plan, children, research_request_kind, open_questions, refusal }.

- workflow: github-pr.yaml
  inputs:
    pr_number: "{{ feature_pr_creator_github.output.pr_number }}"
    // WF0021: GithubPrInput requires { pr_number, branch_name, target_branch,
    //         work_item_id, review_policy } — call site missing 4 of 5.

These are exactly the runtime-discovery defect classes that today require a fresh harness run or a production dispatch to surface.

7 · What the full DSL would look like (if Phase 3+ ever happens)

This is included so the shape is concrete enough to argue about — not as a v1 commitment. Inv 2 sketched representative workflows in detail; this is the boiled-down ergonomic posture.

public sealed record RootFallbackGateInput
{
    public required int ActiveWorkItemId { get; init; }
}

public enum RootFallbackDecision { UseActiveItem, Abort, AutoResolved }

public sealed record RootFallbackGateOutput
{
    public required int RootId { get; init; }
    public required RootFallbackDecision Decision { get; init; }
    public required bool AutoPolicyApplied { get; init; }
}

public sealed class RootFallbackGateWorkflow(IPolicyLoader policy)
{
    public WorkflowDefinition<RootFallbackGateInput, RootFallbackGateOutput> Build()
    {
        var wf = Workflow.Define<RootFallbackGateInput, RootFallbackGateOutput>(
            name: "root-fallback-gate",
            version: "2.4.8",
            tools: [ Tool.Twig ]);

        var loadPolicy = wf.Script("load_policy")
            .Invoke(PolyphonyVerbs.Policy.Load)
            .Route(r => r
                .When(x => x.RootFallback.AutoDecide == RootFallbackMode.UseActiveItem, "use_active_item_auto")
                .When(x => x.RootFallback.AutoDecide == RootFallbackMode.Abort,         "abort_auto")
                .Otherwise("prompt_user"));

        wf.Gate<RootFallbackDecision>("prompt_user")
            .Prompt(PromptTemplate.FromMarkdown("prompts/root-fallback-gate.md"))
            .Option("✅ Use active item", RootFallbackDecision.UseActiveItem, "use_active_item_prompted")
            .Option("🛑 Abort",            RootFallbackDecision.Abort,         "abort_prompted");

        // terminals + Export elided
        return wf.Export(/* … */);
    }
}

Three things to notice:

  1. Routes are lambdas over typed outputs. No more {{ load_policy.output.root_fallback.auto_decide == 'prompt' }} — the compiler proves the field exists and the comparison is well-typed.
  2. Gate options bind a typed enum to a route. Exhaustiveness checkable; gate selection persisted as the enum.
  3. The prompt template stays external markdown. Only the contract fragment (output fields, route values, tool restrictions, marker rules) is compiler-owned and injected.

8 · What we must not do

Anti-pattern Pretend the compiler can prove agent honesty. Schema conformance is not truth. Required-field pressure causes models to fabricate. The compiler proves shape; the harness, postcondition verifiers, and journal prove effect. R1 R2
Anti-pattern Replace conductor. Option C is a platform program, not a compiler follow-on. Polyphony would have to rebuild: route engine, gate UI, web dashboard, /api/stop, parallel/for_each, transcript storage, model/provider adapters, retry/repair, sandboxing. Inv 3 R2
Anti-pattern JIT/runtime YAML generation as the default. Hides the executed artifact. Wrecks postmortems. Breaks the harness's "real conductor against real YAML" contract. Breaks AOT posture. JIT is opt-in, narrow, cached. Inv 2 R1
Anti-pattern Big-bang migration. The six giant workflows (plan-level, implement-merge-group, polyphony, ado-pr, github-pr, feature-pr) are ~80% of workflow LOC. Side-by-side pilots only; handwritten YAML stays canonical until ergonomics are proven. Inv 5
Anti-pattern Hide the YAML from operators. Non-C# readability is not a non-goal — it is an operational invariant. Incident response, onboarding, future AI assistants, and adjacent contributors all read the artifact. R3
Anti-pattern Smuggle a second runtime into the IR. Designing the compiler IR around a hypothetical future polyphony-native executor turns compiler-lite into a shadow architecture project. Build for the conductor backend; let the IR evolve only when D-shape pressure actually arrives. R3
Anti-pattern Generate prompt prose. Mission, rubric, examples, anti-patterns, tone — these are the parts that change when models change. Hiding them in the type system slows the iteration loop where it matters most. Compiler owns contract fragments, not bodies. R2
Anti-pattern Auto-expose all ~80 verbs as agent tools. Explodes the action surface, blurs safety boundaries, makes prompt/tool selection harder. Verbs are tool-describable; expose only a curated workflow-specific subset. Inv 4

9 · Risks & tripwires

Each risk has a measurable signal that should fire before scope is expanded.

Risk Severity Tripwire signal
CDKTF wrapper-tax. Compiler-lite ships, but adds no new guarantees over conductor's existing YAML — becomes permanent catch-up cost. High After Phase 1, fewer than 3 distinct lint classes ever fire on the live corpus. Each lint must catch real defects, not just exist.
Two-system tax. Generated and handwritten workflows coexist indefinitely. High If > 90 days after a workflow is "migrated", the handwritten version still exists, treat as a failure of the migration discipline — not a feature.
Framework accretion. Every new workflow shape adds a new contract abstraction; reviewers must learn the framework before reading the workflow. High v1 authoring surface > 15 public primitives, or "add primitive" PRs outnumber "use primitive" PRs for any month.
Pilot proves emitter, not contract drift. Leaf-only pilot creates a false sense of progress. Medium Phase 1.5 ships with only a non-agent pilot. R2 requirement: at least one pilot must include a real agent with malformed-output fixtures.
Diff-noisy generated YAML. Even if semantically correct, reviewers cannot eyeball changes. Medium Any pilot PR where reviewers spend more time reading YAML diff than C# source. Require golden-file diff stability with deterministic formatter.
Source-generator AOT regression. A generator stack break blocks shipping. Medium CI green-streak for AOT publish drops below 90% for any 2-week window. Polyphony.csproj currently has AOT disabled (YamlDotNet); track when this loosens.
Compiler-lite as Trojan horse. Team treats compiler-lite as a station, not a finish line; full DSL pressure becomes irresistible because the metadata exists. Medium "We should just author this one in C#" appears in 3+ PRs before Phase 2 stop/go is run.
Conductor protocol drift. Polyphony silently programs to undocumented conductor quirks faster than conductor can rationalize them. Medium Compatibility tests between repos fail without a cross-repo coordination commit. No quirks-encoded-as-features.
Schema fabrication. Strict required-field pressure causes agents to invent values rather than refuse. Medium Refusal/abstain variants present on < 100% of agent contracts. Or: malformed-output rate in eval suite ticks up after schema tightening.
Conductor on_error lands mid-pilot. Forces route-model churn in the compiler. Low If on_error lands before Phase 3, route error model must be deferred until the new conductor surface is stable.
Three pilot gates — mandatory R1 insists: any generated workflow pilot must pass three gates, not one. (1) C# unit tests on builder/analyzers, (2) golden-diff tests on emitted YAML, (3) harness execution against the emitted YAML using the real conductor engine. Without (3), the pilot only proves the compiler likes itself.

Opportunity cost vs. sibling tracks

The honest framing: compiler-lite is not "instead of" sibling tracks — it is a consumer of them. AB#3255 lands either way. AB#3256 lands either way. AB#3258 lands either way. The journal lands either way. Compiler-lite extends AB#3255 by 2–4 PRs of additional surface. The pilots in Phase 1.5 are the first true net-new investment, and they are deliberately small and reversible.

If compiler-lite is the finish line, total program cost is ~5–9 PR-equivalents. The full DSL endgame is ~20–30+ — a different category of commitment.

ROI estimate (qualified) Inv 5 claims compiler-lite captures ~60–80% of the value for ~10–20% of the cost. R1 and R3 both qualify: directionally believable, numerically aspirational. The more honest framing — compiler-lite captures most of the provable wins; whether it captures most of the ergonomic or architectural value is a separate question that pilots are designed to answer.

12 · Proposed D14 (decision draft)

D14 — Compiler-lite scope

Decision: Polyphony will extend the AB#3255 typed-contract-surface with (a) one named C# DTO per agent output, (b) generated enum overlays for the existing string route discriminants, (c) a generic Roslyn-driven envelope lint resolving every YAML {{ node.output.* }} reference against the declared producer contract, (d) a child-workflow-call lint requiring all declared inputs to be satisfied, and (e) a route-exhaustiveness analyzer over enum routes.

Out of scope (D14): any C# authoring DSL, any runtime/JIT YAML generation, any change to conductor's runtime contract, any resource-ownership-closure claim beyond kind-subset checking, any prompt-prose generation, any auto-derivation of agent tool surfaces from the verb catalog, any replacement of the harness's authoritative role.

Off-ramp clause: D14 may be the finish line. A subsequent decision to promote compiler-lite into a full C# authoring DSL requires a separate ADR informed by (i) at least one leaf pilot and one agent-bearing pilot, each passing the three-gate test bar, and (ii) AB#3256 phases 1–2 landed.

Forward-compat clause: D14 does not commit to Option D (typed plan protocol shared with conductor). The IR is designed to lower to conductor YAML; Option D remains an explicit later decision, not an implicit eventuality.

Appendix · Investigator summaries

Inv 1 — Prior art / industry survey ~3100 words

Surveys CDK, cdk8s, CDKTF, Pulumi, Airflow TaskFlow, Dagster, Prefect, Flyte, Temporal, DBOS, Argo/Hera/Tekton, GitHub Actions, CircleCI orbs, Dagger, Durable Functions, Restate. Identifies two stable industry patterns: typed authoring surface + separate runtime artifact (CDK/Flyte/Dagger) vs. code-is-the-runtime durable execution (Temporal/DBOS). Polyphony's proposal fits the first family. Closest analogs: AWS CDK (structurally), Flyte (operationally), Dagger (ergonomically). Sharpest warning: CDKTF reached deprecation in 2025-12 because it was a thin wrapper without new runtime value — a permanent catch-up tax. Five design choices Polyphony should steal: (1) explicit compile/register phase, (2) L1/L2/L3 construct layering, (3) distinct runtime-known vs. compile-known value types (Output<T>/tokens), (4) artifact/effect-first composition over string envelopes, (5) narrow escape hatches.

Inv 2 — Type-system mechanics in C# ~4900 words

The mechanically deepest report. Sketches representative workflows (root-fallback-gate, feature-pr, implement-merge-group) rendered in a proposed fluent C# DSL backed by source generators and Roslyn analyzers. Surface area: records for contracts, generated descriptors for verbs/workflows, fluent builder for authors. Compile-time wins listed honestly: field existence, type compatibility, route field reads, exhaustiveness, child input completeness, kind-level resource subsetting. Limits called out: prompt truthfulness, raw script bodies, runtime set membership, remote ADO legality, human gate decisions, concrete resource identity. Recommends: build-time YAML emission as the default, JIT only as opt-in narrow specialization, never reflection-first runtime registries. Honest about the gap between enum overlays (cheap, v1) and sealed-record discriminated unions (more invasive).

Inv 3 — Conductor relationship ~3600 words

Maps four options for the conductor boundary. Option A (build-time YAML, conductor stays runtime) — recommended. Captures the workflow-compiler upside with minimal disruption; keeps dashboard, gates, /api/stop, event log, registry, and operator launcher intact. Option B (JIT YAML) — "A but less inspectable", only justified if eliminating source-tree YAML is itself a primary requirement. Option C (polyphony becomes the runtime) — massive scope expansion, would require rebuilding the route engine, gates, web UI, parallel/for_each, cancellation; explicitly not justified by current evidence. Option D (typed execution-plan protocol shared with conductor) — best long-term collaborative architecture, but not the first move. Verdict: A now, D only as a later upgrade path. Three risks to mitigate: dual-source ambiguity, debugging split-brain, generator lock-in to current conductor quirks.

Inv 4 — Agent contracts integration ~3200 words

Argues the highest-value compiler target is the agent contract boundary, not the whole agent. Walks through the architect → write-plan → seed-children trace step by step: rich structured output → Jinja interpolation → CLI string args → verb reparses into JsonDocument → sidecar persistence → next verb reparses again. One named PlannerOutput/PlannedChild DTO would collapse the entire chain. Prompts should remain human-authored prose with compiler-owned contract fragments (output fields, route vocab, marker rules, tool restrictions). Route domains are contracts too — verdict, action, research_request_kind should be enums, not strings. Verb declarations should be tool-describable but only curated subsets are tool-exposed. Bottom line: "declare agent contracts once, then project them into YAML, prompts, scripts, tests, and docs."

Inv 5 — Roadmap / cost / sequencing ~3600 words

Branch-local inventory: 15 workflow YAMLs (14,125 LOC), 295 named nodes, 186 script nodes, 70 human gates, 23 explicit agents, 12 registry PowerShell scripts (2,338 LOC), 111 [Command] methods. Six workflows account for ~80% of LOC. Recommended MVP: compiler-lite — typed C# registry consumed by schema-driven YAML lint and route validation, keeping handwritten YAML as the workflow source. Sequencing: ride AB#3254 (journal), AB#3255 is the substrate, land AB#3256 phases 1–2 before any authoring DSL, AB#3258 lowers cost in parallel, AB#3257 is independent. Appendix · Reviewer summaries

R1 — Type-correctness lens ~2700 words · Verdict: qualify

Endorses compiler-lite / build-time C# authority for contracts and limited workflow emission. Rejects any claim that C# can prove end-to-end workflow correctness, agent honesty, or concrete resource ownership closure.

Specific objections:

  • Enum overlays are not discriminated unions. C# 12/.NET 9 has no native sum types — the gap requires Roslyn analyzers, sealed hierarchies, and switch-expression discipline. Investigator 2's casual jump from enum overlays to "generated unions" is a real complexity step, not a free refinement.
  • D13 effect modeling can prove kind subset and sometimes pattern compatibility — not ownership closure. Resource ids derive from runtime values, scripts are opaque, agents mutate directly. Great hook, not ownership proof.
  • Source-generator + AOT is plausible but not proven for full workflow lowering. Polyphony.csproj currently has AOT disabled (YamlDotNet). "AOT-friendly posture" is true; "AOT-proven workflow compiler" is not.
  • Hard for_each cases (nested fan-out, manual aggregation, branch-exclusive joins) cannot be statically proven correct — only modeled.
  • Mandatory: any pilot must pass three gates — unit tests on builder/analyzers, golden-diff on emitted YAML, and harness execution against real YAML with the real conductor engine. Without (3), pilot proves only that the compiler likes itself.
  • Compiler-lite ROI estimate ("60-80% for 10-20% cost") is plausible but speculative. More honest: captures most of the provable wins; ergonomic/architectural value is a separate empirical question.

Minimum honest stack: (1) typed descriptors + expression-based refs, (2) closed route domains + exhaustiveness analyzer, (3) explicit boundary metadata (codecs, null/omit, branch-exclusive refs).

R2 — Agentic engineering lens ~3400 words · Verdict: qualify

Use C# to declare workflow structure and the smallest reliable agent-contract surface. Do not let the compiler pretend prompts, schemas, or capability declarations are more deterministic than production LLM systems are.

Specific objections:

  • Inv 1's prior-art is mostly infra/data orchestration, not LLM-centric systems. Agent workflows fail not because edges are mis-declared but because prompts drift, schema pressure causes fabrication, tool surfaces are too wide, retries make outputs worse, models upgrade.
  • Agent<TPromptContext, TOutput> is too small. Real agent nodes need execution mode, curated tool bundle, retry/repair policy, refusal/insufficient-context mode, transcript retention, postcondition checks, model selection.
  • Required-field pressure causes fabrication. Need strict route-critical core, optional advisory periphery, explicit refusal/abstain/error variants on every agent contract. "Hard-fail-everything" is too brittle; silent coercion is dangerous.
  • Capability profiles are descriptive unless enforced. Prompt instructions do not secure tools. Without sandboxing/allowlists, it is documentation plus a basis for audit/postconditions — not enforcement.
  • Pilot strategy is incomplete. A non-agent leaf workflow validates the emitter, not the agentic question. Demand a parallel pilot with at least one real agent contract: typed output, downstream consumer, malformed-output fixtures.
  • Eval infrastructure should be a first-class milestone — prompt snapshotting, malformed-output fixtures, route-regression tests, model-upgrade rebaseline loop — before any serious DSL pilot.
  • Order of effectiveness for trust: sandbox/allowlist > postconditions+audit > prompt restrictions. Be honest about that.

If only three things at the agent boundary: (1) output contract with route-critical core + explicit refusal variant, (2) capability/tool surface with scope + postconditions, (3) consumer binding map with codecs and marker/invariant rules.

R3 — Long-term architecture lens ~2900 words · Verdict: qualify

Pursue compiler-lite and possibly build-time compilation to conductor artifacts. A full C#-first authoring model is defensible long-term only if it stays narrow, operationally transparent, and reversible.

Specific objections:

  • The CDK/Pulumi analogs are products with platform teams. Polyphony is one human plus AI assistants moving fast — same architecture becomes a year-2 burden in a smaller repo. The maintenance math is different.
  • L1/L2/L3 layering is valuable only if 90% of new workflows can be authored without touching the layer definitions themselves. Otherwise it is how internal DSLs become frameworks only their author can extend.
  • Source-generator + analyzer + DSL is really four systems (contracts, builder, generators, artifacts). Not free infrastructure. .NET ecosystem (Native AOT, trimming, System.Text.Json source-gen) repeatedly shows the tax.
  • "Non-C# authors are a non-goal" is dangerous. Over 3-5 years the audience is operators, incident responders, onboarding contributors, adjacent contributors, and future AI assistants — all of whom benefit from a legible compiled surface.
  • Counter and resource-budget modeling are exactly where pragmatic compilers turn into bespoke orchestration languages. Restrain aggressively.
  • Conductor relationship is healthy only with boundary governance: versioned compatibility, source-map guarantees, node-identity stability, no programming to undocumented quirks.
  • Compiler-lite must be a real off-ramp, not a station. Bless the possibility that it is the finish line. Teams often say "we'll just add a thin typed layer" and then the pressure to author code-first becomes irresistible — CDKTF trajectory.
  • Day-1 fine, year-2 wound callouts: "checked-in generated YAML for now" tends to become permanent; "runtime fallback JIT" becomes the hidden execution path; "non-C# authors not a goal" hurts on-call; enum overlays become a constant tax as DTOs evolve; prompt fragments expand into prompt frameworks.

Three sustaining-engineering invariants: (1) operational truth must be inspectable without compiler expertise, (2) most workflow changes must not require compiler changes, (3) migration must stay reversible and single-source-per-workflow.

  3. Refusal/abstain variant shape. Should every agent contract carry a standard AgentRefusal variant, or per-agent custom shapes? R2 argues for mandatory; v1 mechanism not yet specified.
  4. Source-map fidelity — how deep should runtime-failure-to-C#-line mapping go? Comments in emitted YAML? Sidecar map file? Both?
